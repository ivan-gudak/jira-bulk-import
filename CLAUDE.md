# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Set up environment
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # or requirements.txt, without pytest

# Run the tests
python -m pytest

# Run importer (from project root)
./runme.sh                              # needs VAULT_PATH; exports to $VAULT_PATH/_archive/jira-snapshots
./runme.sh --force                      # extra flags are forwarded
python src/main.py                      # uses .jira.ids, exports to .data/
python src/main.py path/to/custom.ids   # custom IDs file
python src/main.py --export-dir=output  # custom export directory
```

The script must be run from the project root — `JiraAuth` and a relative `--export-dir` resolve against `os.getcwd()`. `--export-dir` is rejected when it is empty or would create a new directory at the filesystem root, which is what an unset `VAULT_PATH` leaves behind once `runme.sh` expands `"$VAULT_PATH/_archive/jira-snapshots"`; `runme.sh` checks `VAULT_PATH` up front for the same reason. `runme.sh` already passes `.jira.ids` as the IDs file, so it forwards flags only — a second IDs file is an argparse error.

## Configuration

Credentials are read from `.jira.config` (key-value, `KEY: value` format) or env vars `JIRA_SERVER`, `JIRA_EMAIL`, `JIRA_TOKEN`. The env vars are used only when all three are set; otherwise the file is read and its values replace them. Both `.jira.config` and `.jira.ids` are gitignored and must never be committed.

### Values tied to one Jira site

`SERVER` in `.jira.config` is used only to connect. Every link written into the export is built from `JIRA_BASE_URL` in `src/config.py`, hard-coded to `https://dt-rnd.atlassian.net`. Update it there if the Jira instance changes. The custom field IDs in `FIELD_MAPPING` belong to that site too, and `markdown_generator.py` also uses some directly: Status details (`customfield_19200`), the release-notes fields (`customfield_15900`, `_22157`, `_20300`, `_19502`, `_19701`, `_15000`) and the Architecture / Execution Assignee person fields (`customfield_21107`, `_19400`).

## Architecture

`main.py` orchestrates everything: reads `.jira.ids`, authenticates via `JiraAuth`, then for each ID that is not throttled calls `import_ticket()` and `generate_snapshot_index()`. A failing ticket is logged and the rest continue. At the end `generate_report()` rewrites the top-level index.

Each run uses one timestamp, `YYYY-MM-DD HH-MM-SS` in the machine's local time, and writes under `<export-dir>/<ID>/` (default `.data/`):

- `<ID> - <timestamp>.md` — the snapshot (generated by `MarkdownGenerator`)
- `Comments/<ID>-comments-<timestamp>.md` — comments (generated by `CommentsHandler`), transcluded into the snapshot with `![[...]]`
- `attachments_shared/<sha256_8>_<filename>` — attachment files, plus `.attachment-ids.json` (see Attachments below)
- `<ID>-snapshot-index.md` — this item's snapshot history (generated by `report_generator.py`)

and `<export-dir>/jira-export-index.md`, the top-level index.

`should_skip()` derives the last export time from the newest `<ID> - <timestamp>.md` file name, read as local time, so deleting or renaming snapshot files changes throttling.

**Module responsibilities:**

| Module | Role |
|---|---|
| `main.py` | CLI, `.jira.ids` parsing (`read_jira_ids`), throttling (`should_skip`), `--export-dir` validation, per-ticket import |
| `config.py` | `FIELD_MAPPING` (display name → Jira field ID), `EXPORT_FIELDS` (ordered list for frontmatter), `JIRA_BASE_URL` |
| `jira_auth.py` | Reads credentials, returns a `JIRA` client |
| `markdown_generator.py` | Builds the snapshot: YAML frontmatter + body sections, with a Details fallback for an empty description; orchestrates attachment download |
| `attachment_handler.py` | Downloads attachments into the shared pool; rewrites inline `!image.png!` refs as Obsidian embeds and links |
| `comments_handler.py` | Fetches comments via Jira API, formats each as markdown |
| `field_formatter.py` | Formats individual field types (users, arrays, parent links, linked issues) |
| `jira_markup_converter.py` | Converts Jira wiki markup and ADF → markdown. Shared with jira-workitem-import (see below) |
| `report_generator.py` | `jira-export-index.md` (configured and orphaned items) and the per-item snapshot indexes, read from file names and frontmatter |

**Attachments:** `main.py` always passes a shared pool, so every file is stored as `<sha256_8>_<filename>` in `<export-dir>/<ID>/attachments_shared/`. `attachments_shared/.attachment-ids.json` maps Jira attachment IDs to pool filenames across runs; an ID whose file is still in the pool is reused without downloading (an attachment ID always names the same content). The per-run `Attachments/<timestamp>/` path is still passed to `AttachmentHandler`, but only its non-pool write path, unused by `main.py`, would create it. Links use Obsidian wikilinks, which resolve by file name.

**No PII scrubbing.** Unlike jira-workitem-import, names and emails are exported as Jira returns them.

**The shared converter.** `jira_markup_converter.py` is a copy of the one in `../jira-workitem-import`. The two differ only in `_format_issue_link` and the comment describing it (a Jira URL link here, a wikilink there); this copy uses CRLF line endings. Make a converter change in both copies — the drift test lives in jira-workitem-import (`test_converters_differ_only_in_known_hunks`).

**Adding a new Jira field:** Add the display name → field ID mapping to `FIELD_MAPPING` in `config.py`, then add the display name to `EXPORT_FIELDS` in the desired position. If the field needs special formatting, add a case in `MarkdownGenerator._extract_field_value()` and a helper in `FieldFormatter`.
